# CI 流水线自动 Triage 功能介绍

## 这是什么

CI 流水线自动 Triage 是一项面向团队研发流程的智能处理功能。当你提交的代码合并请求（MR）触发 CI 流水线后，如果流水线失败，系统会**自动检测失败、按失败类型分类、并通过飞书向你推送一张带修复按钮的卡片**。

你不需要主动去 GitLab 查流水线状态，也不需要在大量 CI 日志里翻找错误。收到飞书卡片后，看一眼就知道哪里挂了、大概是什么问题，然后点一下按钮，Agent 就会自动去修。

**一句话总结：流水线挂了 → 飞书自动通知你 → 你点按钮 → Agent 自动修。**

---

## 1. 为什么需要这项功能

在日常研发中，代码推送到 MR 后 CI 流水线会自动跑编译、单元测试、代码检查、构建等任务。某个 Job 挂了之后，你通常需要：

1. 自己发现流水线失败了（可能没人提醒你）
2. 登录 GitLab
3. 在一堆 Job 里找到哪个红了
4. 点进去翻日志
5. 在几千行日志里找到真正的 error 行
6. 想清楚怎么修
7. 改代码、推代码、等流水线重跑

这个过程又长又重复——尤其是编译错误、格式问题这类常见故障，每次都要走一遍同样的流程。

自动 Triage 把**发现问题→通知你→提供修复入口→执行修复**全部整合到飞书里，你不用切到 GitLab，不用翻日志，点一下按钮就行。

---

## 2. 这项功能如何工作

整个过程分两个阶段：

### 阶段一：自动检测 + 飞书通知（不需要你做任何事）

```
CI 流水线失败
  ↓ 系统自动触发
递归扫描所有失败 Job（含下游子流水线）
  ↓
按失败类型分类（format / clang / build / 未知）
  ↓
识别 MR 作者 → 映射到飞书账号
  ↓
推送飞书卡片（含失败原因 + 针对性的修复按钮）
```

**关键点**：这一步只做"快速分类"——看失败 Job 的名字，判断是格式问题、编译问题、还是其他问题，然后给你推一张卡片。卡片里不会有详细的日志分析（那需要 LLM 花时间），只有分类结果和按钮。

### 阶段二：Agent 自主诊断 + 修复（你点按钮后触发）

```
你点击飞书卡片上的修复按钮
  ↓
Triage Agent 启动（ReAct 模式，自主决策）
  ↓
Agent 自己决定下一步做什么：
  - 先查流水线失败日志 → 看看具体什么错误
  - 克隆你的代码 → 看看出错的文件
  - 读文件内容 → 理解问题
  - 构造修复任务 → 委托 Hermes CLI 生成修复代码
  - 推送修复 → 等流水线重跑
  - 如果又挂了 → 按根因重新分组；有新证据时再生成下一次修复
  ↓
修复结果通过飞书回发给你
```

**关键点**：Agent 不是走固定流程，而是**自己看一步、想一步、做一步**（ReAct 范式）。它看到编译错误会先读代码再修，看到覆盖率不足会先拉覆盖率报告再补测试。每次修复都有独立 attempt ID；如果连续两次没有产生代码变化或新诊断证据，会停止重复调用 Hermes，转入明确的失败结论。

同一 MR 正在执行 `/auto` 时，triage 不会粗暴中断当前子命令，而是在当前 `review/describe/improve` 子命令结束后暂停
auto、保存进度并优先修流水线。triage 成功或失败后，auto 都从下一个未执行子命令继续；不同 MR 仍可由其他执行槽或
其他 Agent worker 并行处理。

## 3. 你会收到什么

当你负责的 MR 的 CI 流水线失败时，飞书会收到一张卡片，内容大致如下：

> **MR 流水线失败**
>
> **MR:** [修复传感器接口编译错误](https://gitlab.example.com/example-group/example-project/-/merge_requests/42)
> **流水线结果:** 失败
> - 检测到 **build** 相关流水线失败，可尝试自动修复编译错误。
> - 失败 jobs: build, unit_test_coverage
>
> [修复编译错误]（红色按钮）

**卡片上有什么：**
- MR 标题和链接
- 失败的 Job 名称列表
- 失败类型分类（format / clang / build / 未知）
- 针对失败类型的修复按钮

**卡片上没有什么：**
- 不会有大段日志（日志分析是 Agent 点按钮后才做的）
- 不会有详细的错误分析（那是 Agent 的工作，不是通知阶段的工作）

### 按钮是按失败类型给的，不是一股脑全塞给你

| 失败类型 | 卡片上的按钮 | 点击后做什么 |
|---|---|---|
| **format**（代码格式） | [修复格式]（蓝色） | 直接执行确定性格式修复（零 LLM 成本，秒级完成） |
| **clang**（静态分析） | [修复 clang 问题]（红色） | 启动 Triage Agent 自主诊断修复 |
| **build**（编译失败） | [修复编译错误]（红色） | 启动 Triage Agent 自主诊断修复 |
| **未知类型** | [自动诊断修复]（红色） | 启动 Triage Agent 自主诊断修复 |

如果同时有多种失败（比如 format + build），会同时显示多个按钮，你按需选择。

### 没有点击修复时，成功流水线不会发消息

系统只为初始 `failed` 流水线推送失败卡。普通成功、运行中、取消流水线不会打扰你；但你点击修复后，最终成功或失败都会
收到一张终态卡，避免原卡静默更新后用户不知道任务已经结束。

## 4. 你应该怎么用

**三步：查看 → 确认 → 点击**

### 第一步：看卡片

收到飞书卡片后，看一眼：
- 是哪个 MR 挂了
- 是什么类型的失败（format / clang / build / 未知）
- 哪些 Job 失败了

### 第二步：判断要不要让 Agent 修

- **format 问题**：直接点"修复格式"，秒级完成，不需要犹豫
- **编译错误**：如果你大概知道是什么问题（比如少了个 include），点"修复编译错误"让 Agent 去修
- **未知问题**：如果不确定，可以先点 MR 链接去 GitLab 看看，再决定要不要让 Agent 修

### 第三步：点按钮

点击后，飞书会提示"已触发修复，结果稍后私聊发送"。Agent 开始工作，你该干嘛干嘛去。

### 修复完成后

整个交互严格只有两张卡：最初的流水线失败卡会持续更新状态；修复终态（成功或失败）会再发送一张完整结果卡。不会再单独
发送 `Received command ... Processing` 或“正在修复”消息。终态卡会带 MR、任务 ID、每次提交、root/validation
pipeline、coverage（或没有数据的原因）以及从点击到终态的分段耗时。

Agent 修完后会通过飞书给你发结果：
- **成功**：告诉你修了什么，流水线已通过
- **失败**：告诉你试了几轮、为什么没修好，建议你手动处理

## 5. 这项功能能带来什么帮助

### 更快知道哪里挂了

不用登录 GitLab、不用翻 Job 列表。卡片直接告诉你"build 类型的失败，挂在 build 这个 Job 上"。

### 不用翻日志

Agent 会自动读 CI 日志、提取关键错误行、过滤无关内容。你不需要在几千行日志里找 error。

### 点一下就修

format 问题秒级修复；编译错误、测试失败由 Agent 自主诊断并修复。你不用切到 GitLab 改代码再推。

### 全程在飞书里完成

通知、修复入口、修复结果都在飞书里。不用在飞书、GitLab、CI 页面之间来回切。

### 处理链路对比

**原来：**
发现流水线失败 → 登录 GitLab → 找失败 Job → 翻日志 → 分析原因 → 想方案 → 改代码 → 推代码 → 等重跑

**现在：**
收到飞书卡片 → 看一眼 → 点按钮 → 等结果

## 6. 你需要配合什么

### 保证 GitLab 账号关联了飞书

系统通过 GitLab 用户名映射到飞书账号（通过邮箱自动匹配）。如果你的 GitLab 邮箱和飞书邮箱不一致，卡片可能发不到你手上。**如果收不到卡片，找管理员配置用户映射。**

### 及时看卡片

收到通知后尽量及时处理，避免失败的 MR 一直挂着影响合并。

### 判断要不要让 Agent 修

Agent 能处理大部分常见问题（编译错误、格式问题、测试失败、覆盖率不足），但不是所有问题都能修。如果涉及复杂业务逻辑或外部服务异常，Agent 修不了，你需要自己处理。

### 关注修复结果

Agent 修完后会发飞书消息告诉你结果。如果修好了，确认一下流水线确实通过了；如果没修好，看看 Agent 的分析，自己接手处理。

---

## 7. Agent 能修什么、不能修什么

### 能修的

| 问题类型 | 修复方式 | 典型耗时 |
|---|---|---|
| 代码格式问题 | 确定性修复（下载格式报告，直接改） | 秒级 |
| 编译错误（缺少 include、类型错误等） | Agent 读代码 → 定位错误 → 生成修复 → 推送 | 3-10 分钟 |
| 单元测试失败 | Agent 分析失败用例 → 修复测试逻辑 → 推送 | 5-15 分钟 |
| 覆盖率不足 | Agent 拉取未覆盖行报告 → 补充测试用例 → 推送 | 5-15 分钟 |

### 不能修的

- **业务逻辑错误**：Agent 不知道你的业务意图，不能判断"这个返回值对不对"
- **外部服务异常**：比如 CI 环境的 Docker 挂了、网络不通、依赖仓库不可达
- **多个相互关联的复杂问题**：Agent 一次聚焦一个问题，多问题交织时容易顾此失彼
- **缺少当前代码与 CI 证据的问题**：Agent 不会猜测或读取以前测试留下的修复答案；证据不足时会停止并说明原因

遇到这些情况，Agent 会告诉你"我修不了，原因是 XXX"，你接手处理就行。

## 8. 技术说明（给好奇的人）

### Agent 是怎么工作的

Agent 采用 **ReAct（Reason + Act）范式**——不是走固定流程，而是**看一步、想一步、做一步**：

1. **观察**：查流水线日志、读代码文件、看覆盖率报告
2. **思考**：根据观察结果，决定下一步做什么
3. **行动**：调用一个工具（克隆代码、读文件、生成修复、推送、等流水线）
4. **再观察**：看工具返回的结果，回到第 1 步

Agent 可使用查流水线日志、查覆盖率、读仓库文件、拉依赖文件、分析 diff、准备当前代码快照、调用 Hermes、提交推送、
等待流水线和结束等工具。父流水线只负责生成下游任务时，Agent 会继续定位真正包含 build/coverage/format Job 的 validation
子流水线，不会把 `generate_joblist` 亮绿误判成修复成功。

### 两层 Agent 架构

- **外层 Triage Agent**：负责诊断、根因分组、决定下一步和验证终态
- **内层 Hermes CLI**：只在当前隔离 workspace 中搜索和修改代码

外层 Agent 不直接写代码，而是把当前流水线证据和当前仓库快照组成具体任务，交给 Hermes CLI 执行。每轮提交按
`task + attempt + diff` 生成独立幂等身份，因此第二轮真实变更可以创建第二个 commit，而任务重试不会重复创建同一 commit。

### 日志可追溯

Agent 的诊断、工具调用、push attempt、pipeline group 和阶段耗时都有任务级日志与 Redis 状态，worker 重启后仍可恢复和审计。
日志不会作为下一次 revert 测试的答案输入，Hermes 每次只能依据这次任务准备出的当前代码快照。

## 9. 总结

| | 传统方式 | 自动 Triage |
|---|---|---|
| 发现失败 | 自己去 GitLab 看 | 飞书自动通知 |
| 定位问题 | 翻 Job 列表 + 翻日志 | 卡片直接告诉你 |
| 分析原因 | 自己读日志 | Agent 自动分析 |
| 修复代码 | 自己改 + 推 | 点按钮，Agent 自动修 |
| 验证结果 | 等 GitLab 流水线 | Agent 等完，飞书通知你 |
| 全程操作位置 | GitLab + CI 页面 + 日志页面 | 飞书 |

**一句话：流水线挂了不用管，飞书会告诉你，点一下按钮 Agent 帮你修。**
